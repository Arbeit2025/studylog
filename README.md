# studylog

studylog は、Flask と SQLite で作られたシンプルな学習ログアプリです。
  
ブラウザから学習前の計画を保存し、学習後に同じログへ結果を追記できます。
一覧では前後の変化、表示範囲内の合計学習時間、平均集中度・平均理解度を確認できます。

小さくてシンプルな学習ログを目的としています。


Flask + SQLite study log app. Phase 0 / v0.9（内部テスト版）。

Phase 0の項目別確認と機能一覧は [docs/phase0.md](docs/phase0.md) を参照してください。

## Features
- 学習内容、カテゴリ、目標、予定時間、学習方法の保存
- 学習前の集中できそう度・理解度・自信度（1〜5）の保存
- 学習後の実際の時間・集中度・理解度・自信度、振り返りの保存
- 学習前後の確認テスト得点（0〜100点換算、任意入力）の保存
- 学習前だけの保存、途中保存、学習後の追記・編集・削除
- 理解度・自信度・確認テストの前後差、予定時間と実績の比較
- 期間・カテゴリでの絞り込みと、学習完了のログを対象にした時間・平均の集計
- 同じカテゴリの直前5件と、時間・集中度・理解度・自信度・確認テストの比較
- 状態の暫定分類、判定理由、比較データの充足度、4種類の支援の方向の表示
- 本人の同じカテゴリの過去記録を使う個人別の判定基準
- 状態に応じた次回の予定時間・目標・方法の自動補正と、新しいログへの引き継ぎ
- 採用した補正計画・比較元の保存、学習後の比較、カテゴリ別の継続評価
- ライト／ダーク表示の切り替え、端末のテーマへの追従、ブラウザごとの設定保存

## 表示テーマ
ログイン・一覧・編集画面の「テーマ」で「ライト」「ダーク」「端末に合わせる」を
選べます。初回は端末の設定に合わせ、端末側の変更にも追従します。
ライト／ダークを明示的に選ぶと、端末の設定よりもその選択を優先します。

設定は同じブラウザ・同じサイトの `localStorage` に保存します。再読み込み、
画面移動、ロック解除後も引き継ぎ、同じサイトを開いた別タブにも反映します。
ブラウザのデータを消した場合は初期設定に戻り、別の端末には同期しません。
保存が制限されたブラウザでも、その画面での切り替えは利用できます。

## 記録の流れ
サイトを開いたら、数字4桁の暗証番号でロックを解除します。解除後は同じ
ブラウザのセッション中、最長12時間利用できます。一覧・編集画面の「ロック」で
すぐに入り直せます。ブラウザがセッションを復元する場合もあるため、利用を
終えるときは「ロック」を使ってください。

1. 学習内容と学習前の計画・評価を入力し、「学習前を保存」を押します。
2. 一覧の「学習後を記録」を開き、実際の学習時間と学習後の結果を入力します。
3. 「学習後まで保存」を押すと、同じログが学習完了になります。
4. 一覧の「次回計画の自動補正」を確認します。「この計画で次の学習を準備」で
   次の入力欄へ引き継ぎ、必要なら編集して「学習前を保存」で保存します。
5. 引き継いだログに学習後の結果を保存すると、「この補正計画の評価」と
   「補正効果の継続評価」に変化が表示されます。

学習後に前後の情報をまとめて保存することもできます。実際の学習時間は
学習完了時に1分以上の整数が必須です。評価と確認テストは任意で、未入力は
未測定として保存します。前後両方が記録された項目だけ差分を表示します。
学習前の集中できそう度は予測値、学習後の集中度は振り返りの評価です。

## 状態分類と過去ログ比較
一覧の各ログで状態の候補と支援案を表示します。「比較の内訳」を開くと、
各項目の今回値、過去平均、差、比較件数、比較に使ったログを確認できます。

- 基準値は同じカテゴリの完了ログのうち、学習日が古い順・同日はID順で
  そのログより前にある直近5件の平均です。本人のDB内だけで計算し、別カテゴリ、
  学習中、対象ログ自身、後続ログは混ぜません。カテゴリ未設定は未設定同士で比較します。
- 表示期間の絞り込みとは独立して基準値を計算します。編集・削除・過去日付での
  追加は、次の表示時に後続ログの比較にも反映されます。
- 未測定・範囲外・不正な旧値は項目ごとに除外します。0点は有効です。
  過去5件の中に未測定値があっても、それより前のログで埋めません。
- 過去との差に `min(その項目の比較件数 / 5, 1)` を掛けて少数記録の影響を弱めます。
  過去傾向の判定はその項目が3件以上あり、補正後の差が±1段階以上のときです。
  表に出す差は補正前です。「比較データの充足度」は評価3項目の最少比較件数で示し、
  判定の正答確率や統計的信頼区間を意味しません。

試作ルール `state-v1` は次の順で最初に一致した状態を表示します。

| 優先順 | 状態候補 | 条件 | 支援の方向 |
| --- | --- | --- | --- |
| 1 | 自己評価のずれ | 自信度と確認テスト参考換算値との差が±1.5段階以上。テスト未記録なら理解度との差 | 自己認識の促進 |
| 2 | 理解の停滞 | 理解度が2以下、または補正後の過去差が−1以下 | 学習機会の提供 |
| 3 | 実行・集中の見直し | 集中度が2以下、または補正後の過去差が−1以下 | 個別のフィードバック・介入 |
| 4 | 自信の低下 | 自信度が2以下、または補正後の過去差が−1以下 | 自己認識の促進 |
| 5 | 前進傾向 | 学習後の3評価があり、理解度または集中度の補正後の差が＋1以上 | 学習状況の可視化 |
| 6 | 大きな変化なし／今回の評価は中程度以上（暫定） | 学習後の3評価が3以上で、上の条件に一致しない | 学習状況の可視化 |

学習中は判定待ち、評価不足でどの条件にも当てはまらない場合は判定保留です。
確認テストの参考換算は `1 + 得点 / 25` です。テストの内容や難易度の違いは
補正していません。閾値・換算式は今回定めた試作仕様で、検証済みの能力尺度ではありません。
学習時間は比較表示だけに使い、長短をそのまま良否や計画の達成度に置き換えません。

卒論由来の4分類は「支援の方向」です。状態分類そのものの4分割ではありません。
分析は読み取り時に再計算し、元の評価・メモを変更しません。分析結果の固定保存、
支援の採否・結果を学習した動的補正は今回の実装には含みません。

## 個人別の判定基準と次回計画の自動補正
個人別の基準は、上記の本人・同じカテゴリ・直前5件の平均と、項目別の記録数です。
全利用者共通の固定平均と比べる方式ではありません。状態の判定式・閾値自体は
共通の試作ルールで、手動で閾値を設定する機能や、機械学習による最適化はありません。

次回計画 `plan-v1` は、完了した各ログの分類と過去比較から自動生成します。
学習中、学習日が不正、実際の時間が不正、状態が判定保留のログは生成を待ちます。

- 時間の基準は今回の予定時間を優先します。予定が未記録なら、比較対象の過去5件以内に
  有効な時間が3件以上ある場合はその平均、2件以下なら今回の実際の時間です。
- 重み `w = min(3評価の最少比較件数 / 5, 1)` を使います。
  「理解の停滞」「実行・集中の見直し」では、基準時間に `0.90 - 0.15*w` を掛けます。
  過去記録なしは10%、各5件なら25%の短縮です。
- 「前進傾向」で各3件以上の比較があり、今回の3評価がすべて4以上の場合だけ、
  基準時間に `1 + 0.10*w` を掛けて最大10%増やします。それ以外は時間を維持します。
- 分単位で四捨五入し、次回案は1〜480分に収めます。元の時間を変更する制限ではありません。
- 目標は利用者が書いた「次回どうするか」を優先し、なければ状態に応じた小さな目標を
  提案します。「大きな変化なし」「前進傾向」では既存の学習方法も引き継ぎます。
  その他は分類に対応した支援案を学習方法にします。理由は各ログの「補正の理由」で確認できます。

表示時に再計算するため、過去ログの編集・削除は次の表示に反映します。
フィルタ、別カテゴリ、学習中、対象より後の日付・同日の後続IDは基準に混ぜません。
学習時間の長短だけで成功・失敗や達成率を推定しません。
これらの補正幅は試作仕様で、学習効果が検証された最適値ではありません。

引き継ぎは `/?plan_from=<ログID>` で入力欄を準備するだけで、GETではDBを書き換えません。
次の保存で予定時間・目標・方法が通常の学習前データとして新しいログへ残ります。
元の評価・メモ・自分で書いた次回計画・日時を上書きせず、前回の得点・評価・実績時間も
次のログへコピーしません。元ログを削除しても、保存済みの次回計画は保持します。
採用時の提案と比較元は、次節の継続評価用に固定保存します。

## 補正効果の継続評価
「この計画で次の学習を準備」から引き継いで保存したログが対象です。
画面を開くだけでは採用履歴を作りません。保存時に、元ログのID・学習日・カテゴリ、
プレビュー時点の学習後の値、提案の方式・予定時間・目標・方法・理由、採用日時と
実際に保存した計画を `plan_tracking` に残します。提案を編集して保存した場合も区別します。
プレビューには署名を付け、改ざんや署名鍵変更後の古い引き継ぎはHTTP 400で拒否します。
比較元が保存前に削除された場合も保存を拒否し、部分的なログは作りません。

学習中は結果待ちです。完了後は集中度・理解度・自信度・確認テストについて、
採用時の比較元と今回の学習後の値の差を項目ごとに示します。
理解度・自信度・テストは今回の学習前後差も表示します。学習前の集中できそう度は
予測なので、集中度の前後差には使いません。未入力・範囲外の旧値は項目単位で除外し、
0点や小数点は有効値として扱います。学習時間だけで成功・失敗を判定しません。

- 差が正の項目だけなら「比較値が上昇」、負の項目だけなら「比較値が低下」、
  両方あれば「上昇・低下が混在」、すべて0なら「比較値に変化なし」と表示します。
  比較可能な項目がなければ保留します。差の大小への有意差検定は行いません。
- 「補正効果の継続評価」は表示中のログが対象です。カテゴリ別に、項目ごとの
  差の平均と有効な比較件数、直近5件までの変化を学習日・同日のID順で表示します。
  各ログは1件と数え、再編集で採用数を増やしません。
- 採用後にカテゴリを変更した場合や、学習日を比較元より前へ変更した場合は
  評価を保留し、集計へ混ぜません。元に戻せば再評価します。
- 元ログの編集・削除でも採用時の比較元と提案は保持します。今回の結果を編集・削除すると
  次の表示で評価・集計を再計算します。保存済みの次回計画は後から自動で書き換えません。
- 旧ログや、引き継ぎを使わず手動保存したログには、採用の関係を推測して付けません。

これは `effect-v1` という観察用の試作機能です。自己評価や難易度の異なるテストを含むため、
記録上の変化が補正によって起きたと確定するものではありません。
学習効果の実証や、結果に応じて判定閾値・補正係数を自動学習する機能は含みません。

## データの保存
標準ではアプリと同じディレクトリの `studylog.db` に保存します。
`STUDYLOG_DB_PATH` で保存先を指定できます。相対指定はアプリの場所を基準に解決します。
全機能が同じDBの `logs` テーブルを使用します。
起動時にバージョン付きマイグレーションを実行し、不足する列を追加します。
既存DBの構造を変更する前には `backups/` にSQLiteのオンラインバックアップを作成します。
バックアップに失敗した場合は構造を変更せず起動を中止します。以前の記録は学習完了として
引き継ぎ、存在しない学習前の評価・得点・保存日時は補いません。
旧 `study_logs` テーブルや別DBからの移行は、元データの確認後に明示的に実行します。

### バックアップと旧データの移行

管理者ログイン後、一覧または管理者画面の「バックアップ」から現在のDB全体をダウンロードできます。
WALモードでもコミット済みの内容を取り込みます。ファイルには学習記録が含まれるため、
公開リポジトリへ追加せず、自分で管理する場所に保管してください。

サーバー上のCLIでも実行できます。

```bash
flask --app soapp backup-databases
flask --app soapp import-legacy /absolute/path/to/srl_log.db --table study_logs
flask --app soapp import-legacy /absolute/path/to/old-studylog.db --table logs
```

バックアップコマンドは、設定されたDBと、プロジェクト内でSQLiteのヘッダーを持つファイルを
対象にします。既存の `backups/`、仮想環境、Git内部は探索対象から除きます。
移行前には移行元・移行先をそれぞれバックアップします。旧テーブルと元DBは削除しません。
IDの衝突時は既存ログを保持し、移行したログに新しいIDを付けます。
同じファイル・テーブル・元IDの再移行は重複を作りません。移行済みの元データに変更があれば、
自動上書きせず全件をロールバックします。ファイルを改名・移動すると別の移行元になるので、
同じ元ファイルの場所を固定してください。未知の列は元DB・バックアップに保持します。

`study_logs.focus_score` → `logs.concentration`、`understanding_score` → `understanding`、
`reflection` → `memo` と対応づけます。旧形式にない自信度・学習前データはNULLにします。
元データの記録値・日時は推測で書き換えません。

DBが再起動や再デプロイ後も残るかは、配置先のストレージに依存します。
自動バックアップを同じ一時ディスク上に作るだけでは永続化になりません。
Render等で運用する場合は永続ストレージを確認し、ダウンロードしたバックアップも別に保管してください。

学習状態は `status`（`in_progress` / `completed`）、前評価は
`before_concentration` / `before_understanding` / `before_confidence`、後評価は
既存の `concentration` / `understanding` / `confidence` に保存します。
得点は `before_test_score` / `after_test_score`、前後の初回保存日時は
`before_saved_at` / `after_saved_at`、最終更新日時は `updated_at` です。
新しい保存日時はUTCのISO 8601形式です。既存の日時はそのまま保持します。

## 暗証番号の設定
暗証番号は画面や公開ソースに埋め込まず、サーバーの環境変数で設定します。

| 環境変数 | 設定内容 |
| --- | --- |
| `STUDYLOG_PIN` | 半角数字4桁（先頭の0も可） |
| `STUDYLOG_ADMIN_PASSCODE` | 管理者用の半角英数字8文字。大文字・小文字を区別 |
| `STUDYLOG_SECRET_KEY` | セッション署名用のランダムな秘密鍵。32文字以上 |
| `STUDYLOG_COOKIE_SECURE` | 通常は未設定（HTTPS専用Cookie）。ローカルHTTPで試す場合だけ `0` |
| `STUDYLOG_DB_PATH` | 任意。使用するSQLiteの保存先（標準はアプリ直下の `studylog.db`） |

Renderでは既存の `studylog1` サービスのEnvironmentへ設定します。環境変数を
保存した後、その設定を取り込むデプロイを実施してください。PINや秘密鍵を
README、テスト、`.env` 等へ書いてコミットしないでください。

PINまたは秘密鍵が未設定・不正ならHTTP 503で閉じ、ログの表示・変更を許可しません。
PIN・秘密鍵を変更すると、既存の解除済みセッションも無効になります。
ログの一覧・編集だけでなく、追加・更新・削除への直接アクセスもサーバー側で保護し、
すべてのPOSTフォームでCSRFトークンを確認します。

5回連続で入力を間違えると、30秒間は正しい番号でも解除できません。
最後の誤入力から5分空いた場合は、連続失敗数をリセットします。制限は
SQLiteの専用テーブル `studylog_auth_attempts` で共有するため、Cookieの削除や
プロセスの再起動では解除されません。1人用の簡易ロックなので、別の訪問者による
誤入力でも一時的に待機が発生します。再デプロイ後の制限の保持はDBの永続性に依存します。
4桁PINは簡易的なアクセス制限です。個別アカウント・多要素認証・データの暗号化は行いません。

### 管理者ログイン

入口の「管理者としてログイン」にチェックすると、専用の `/admin/login` へ移動します。
JavaScriptが無効な場合もリンクから開けます。通常の4桁PINとは別の8文字のパスコードを
サーバー側で照合し、成功したブラウザセッションだけに管理者権限を付けます。
通常利用からは一覧・編集画面の「管理者ログイン」リンクでも切り替えられます。

通常ログインでは学習ログの閲覧・追加・編集・削除・分析を利用できます。
DB全体のダウンロード (`/backup`) と管理者画面 (`/admin`) は管理者専用です。
チェック欄・URL・送信フォームの `role` 等で権限を指定しても管理者にはなりません。
管理者パスコードが未設定・不正な場合、その入口は503となりますが通常利用は継続できます。

管理者権限は最大12時間。ロックで通常・管理者の両方を終了し、管理者画面の
「管理者権限を終了して通常利用へ」では管理権限だけを終了できます。
パスコード変更で管理者権限を無効にし、通常PIN・署名鍵の変更でも解除状態を無効にします。
ログイン成功時と管理権限終了時にCSRFを更新し、すべてのPOSTで照合します。
管理者パスコードにも5回失敗・30秒待機・5分の失敗数リセットを適用し、
試行回数は `studylog_admin_auth_attempts` に保存します。通常PINの成功ではリセットできません。
DBの永続性に依存する点は通常PINと同じです。

この権限はStudylog内の認可です。GitHub・Render・ChatGPTの外部権限や操作承認、
OS権限・料金プラン・DBの永続化を変更するものではありません。
管理者コードも通常PINと同様にサーバーの環境変数だけに設定し、公開コードや記録には残しません。

## Run (local)
Python 3.12 / 3.13に対応。Renderの起動コマンドは従来どおり `gunicorn soapp:app` です。
依存バージョンは `requirements.txt` に固定しています。

```bash
pip install -r requirements.txt
python - <<'PY'
import getpass
import os
import secrets
os.environ["STUDYLOG_PIN"] = getpass.getpass("暗証番号（数字4桁）: ")
os.environ["STUDYLOG_ADMIN_PASSCODE"] = getpass.getpass("管理者パスコード（半角英数字8文字、通常利用だけなら空欄可）: ")
os.environ["STUDYLOG_SECRET_KEY"] = secrets.token_hex(32)
os.environ["STUDYLOG_COOKIE_SECURE"] = "0"
from soapp import app
app.run(debug=False)
PY
```
この起動例では秘密鍵を起動時に生成するため、再起動すると入り直しになります。
継続したセッションが必要な運用では、十分にランダムな秘密鍵を環境変数で保持します。

## Tests
```bash
python -m unittest discover -s tests -v
python tests/http_auth_smoke.py
python tests/http_plan_smoke.py
python tests/http_effects_smoke.py
node tests/theme_runtime.js
```
実アプリを一時ディレクトリへコピーし、FlaskのHTTPルートとSQLiteで検証します。
普段使っているDBは変更しません。追加・前後保存・繰り返し編集・再起動・
旧DBの列追加・入力エラー・集計・絞り込み・削除を確認します。
認証テストは専用の仮の番号とランダムな鍵を使います。未解除時の閲覧・変更拒否、
誤入力・形式不正、ロック解除・再ロック、回数制限・待機後の復帰、期限切れ、
Cookie属性・改ざん、CSRF、不正なサーバー設定も検証します。
次回計画について、個人別基準・補正幅・端数・欠測・旧値・過去編集による再計算と、
入力欄への引き継ぎ・保存・再起動後の保持・入力エラー時の保持も確認します。
継続評価は、採用前後の編集・欠測・0点・小数点・複数回の採用・結果編集・
元ログの削除・再起動・カテゴリの区別・項目別件数・署名改ざん拒否を確認します。
Phase 0ではさらに、WALを含むバックアップ、移行の再実行、ID衝突、元データの保持、
同時起動、失敗時の全件取り消し、DB障害時の安全な応答、長すぎる入力も検証します。
`.github/workflows/tests.yml` によりpushとプルリクエスト時に自動実行します。

## コード構成

| 場所 | 役割 |
| --- | --- |
| `soapp.py` | HTTPルート、認証、保存処理の連携、エラー応答、CLI |
| `studylog_db.py` | 共通DB接続、バックアップ、マイグレーション、旧データ移行 |
| `studylog_forms.py` | 入力検証、期間指定、日本時間の日付 |
| `studylog_analysis.py` | 状態分類、次回計画、補正計画の継続評価 |
| `templates/` | ログイン、一覧、編集、共通入力フォーム |
| `static/` | CSS、テーマ切り替え、再表示・削除確認のJavaScript |

HTMLは自動エスケープし、JavaScript・CSSは外部ファイルへ分離しています。
CSPで同一サイトのスクリプトとスタイルだけを許可し、全POSTをCSRFトークンで確認します。
DBエラーは内部パス等を画面に含めず503で返し、書き込みはトランザクションで取り消します。
入力の上限はカテゴリ100文字、メモ10,000文字、その他の文章2,000文字、要求全体256KiBです。
期間指定は日付形式と開始・終了の順序を検証します。「今日」「今週」「今月」は日本時間で計算します。
